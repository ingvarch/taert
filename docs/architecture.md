# Architecture

System design, safety guarantees, and storage algorithms. For usage instructions, see [usage.md](usage.md).

## Components

| Component | Module | Responsibility |
|---|---|---|
| Safety Engine | `crate::core::safety` | Protects critical paths, credentials, symlinks, and cloud files |
| Sizer | `crate::core::sizer` | Measures actual allocated APFS storage blocks with hardlink and clone deduplication |
| Storage Cache | `crate::core::cache` | In-memory tree aggregation and folder snapshot cache |
| Catalog | `crate::core::catalog` | Defines known cache paths, risk tiers, and auto-select defaults |
| Cleaner | `crate::core::cleaner` | Executes safe deletions with live progress and safety checks |
| Startup Manager | `crate::core::startup` | Scans, associates, inspects live metrics, and switches launchd/login items |
| Universal App Slimmer | `crate::core::slim` | Strips Intel x86_64 slices from universal Mach-O binaries preserving code signature and ARM slices |
| Compression Engine | `crate::core::compress` | Safe transparent APFS compression using Apple libcompression and decmpfs ABI |
| iCloud Local Copies | `crate::core::icloud` | Lists the folders of iCloud Drive and its apps and asks iCloud to remove the local copy of files it can download again |
| Admin Helper | `crate::core::admin_helper`, `crate::core::admin` | Compresses or slims one root-owned app bundle in taert run as root |
| Scanner & Purger | `crate::core::scanner`, `crate::core::purger` | Discovers cache categories and project build artifacts |
| Homebrew | `crate::core::homebrew` | Lists installed formulae and casks with sizes through read-only `brew info` and `brew outdated` calls, and removes unused dependencies, old versions, and one formula that nothing uses through brew |
| Orphan Detector | `crate::core::orphans` | Finds files left behind by apps that are gone with Spotlight and bundle ID checks |
| App Controller | `crate::ui::app` | Main Ratatui event loop, key router, and modal overlays |
| TUI Components | `crate::ui::components` | Apple HIG-inspired widgets (AppChrome, Modal, Picker, Button, Gauge, ProgressView) |

## Safety Engine

Disk cleanup tools must never compromise system integrity, user credentials, or remote cloud storage:

1. **System Root Protection**:
   `Safety::is_critical_root` strictly prevents operations on `/`, `/System`, `/Library`, `/Applications`, `/usr`, `/bin`, `/sbin`, `/var`, `/etc`, and user home root `~`. Attempts to delete these paths fail immediately before any filesystem calls.
2. **Credential Isolation**:
   `Safety::is_credential_root` protects identity stores including `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.gpg`, `~/.kube`, `~/.docker`, `~/.claude`, `~/.config`, `~/.cargo`, `~/.rustup`, `~/.gem`, `~/.nvm`, `~/.pyenv`, `~/.rbenv`, `~/.ollama`, `~/.lmstudio`, and `~/Library/Keychains`, except cache folders that stay scannable (`~/.docker/cli-plugins/.cache`, `~/.docker/buildx/cache`, `~/.cargo/registry/cache`, `~/.cargo/registry/index`, `~/.cargo/git/db`, `~/.cargo/git/checkouts`, `~/.ollama/logs`, `~/.lmstudio/server-logs`).
3. **Symlink Rejection**:
   `Safety::has_symlink_component` verifies that no path or parent component is a symbolic link. Deletion operations refuse to follow symlinks to prevent accidental directory traversal outside the intended target.
4. **Cloud Storage & APFS Dataless Protection**:
   `Safety::is_cloud_or_dataless` inspects filesystem metadata for `SF_DATALESS` and checks known sync provider paths (iCloud Drive, OneDrive, Google Drive, Dropbox, Box). Placeholder files with offline data are never removed. Only `taert icloud` asks iCloud to remove local copies, through `Safety::can_evict`.
5. **Path Validation on Deletion**:
   Every file removal re-validates safety rules immediately before `fs::remove_dir_all` or `fs::remove_file` is invoked.

## Docker Cleanup

Docker objects are not files, so they skip the path checks above and go to the daemon instead. `ScanItem::docker` carries a `DockerObject`, and `Cleaner` hands those to `DockerRemover` before any file logic runs. A label that matches a real path can't touch that path.

Rules that keep this safe:

- An object counts as unused only when no container refers to it, stopped containers included. An unknown use count means in use.
- Nothing is removed with `force`, so Docker refuses whatever a container still needs.
- A tag is checked again before removal, because it can move to another image after the scan.
- Volumes are never selected by default, so `--force` can't remove them.
- A daemon that reports no disk usage is an error, never an empty list.
- `DOCKER_HOST` and the Docker context pick the daemon. A remote one stops with an error and never falls back to a local daemon.

The freed size comes from the daemon's totals before and after, because images share layers.

`bollard` stays pinned to 0.19. Versions 0.20 and newer read `/system/df` only in the API 1.52 shape, and a daemon on an older API then comes back empty with no error. Daemons answer an API 1.49 client in the older shape, including Docker 29 and newer.

## App and Browser Caches

[`app_caches.rs`](../src/core/app_caches.rs) adds two groups to the `junk` scan. App caches are the entries of `~/Library/Caches` one level deep. Browser caches are fixed paths per browser, one row each. A browser with two folders keeps the second in `ScanItem::also`, and `Cleaner` checks both before either goes. If one fails during the removal itself, the report counts the row with the bytes of the folder that went, and lists the one that failed. Neither group walks `Application Support`, so profiles are never rows.

- **No double counting**: an entry that a named target covers, or that is the parent of one, is left out. So are `com.apple.*`, `CloudKit`, and `FamilyCircle`.
- **Selection**: `starts_selected(stale, running)` decides. Stale means nothing in the tree changed for 30 days, and anything unreadable counts as changed. Running comes from one process table per scan. An app cache matches its app by bundle id from `find_apps`, and so does a browser. Any program inside a bundle matched this way counts. `find_apps` leaves out Safari and copies outside the app folders, so a bundle with the browser's name counts too. For those bundles only a program in `Contents/MacOS` counts, because `SafariLinkExtension` runs from inside Safari's bundle while Safari is closed.
- **Refused reads**: when macOS refuses a browser folder, the scan carries one note per browser that names Full Disk Access.
- **Safety**: rows go through the same checks as every other row, and `Cleaner` verifies identity before removal.

## Uninstalling Apps

An uninstall has two steps, so nothing is removed before you have seen it:

1. **Plan** ([`uninstaller.rs`](../src/core/uninstaller.rs)): `find_leftovers` in [`leftovers.rs`](../src/core/leftovers.rs) checks exact places and reads single folder levels. It never walks a tree, so a wrong name cannot reach far. Each find carries its `Evidence`, which decides whether it starts selected. The plan is a normal `CategoryScan`, one group per app, so the select screen, `--dry-run`, and `--json` all show the same list.
2. **Run**: `Uninstaller::run` works through the selected rows of the plan.

These rules keep it from removing the wrong thing:

- **Allowed paths**: `Safety::can_remove` refuses `/Applications` and `/Library`, so uninstalling has its own gate, `Safety::can_uninstall`. Outside the home folder it accepts only app bundles and entries right below the folders apps use, such as `/Library/LaunchDaemons`, and never `com.apple.` names. Credentials, cloud files, and the ignore list stay protected.
- **Bundle ids**: an id must look like reverse DNS before it builds a path. A name that continues an id of 3 or more parts counts as proof. For a shorter id it is only a hint that starts unselected, because `com.vendor` could continue into every app of that vendor. Apple ids count as part of macOS unless they are on a short list of apps people install themselves, and a plug-in can claim one only if it continues the id of its app. Data of a helper inside the app counts as proof only if the helper is named after the app, or comes from the same vendor and no other app of that vendor stays.
- **Other apps**: a file that carries the id or name of an app that stays is left alone. A copy of the app, another channel of it, or an app whose id continues this one narrows the plan to the selected bundle. That check runs at planning and again right before the run, and also covers copies the list leaves out.
- **Links**: a bundle that is a link goes alone, with no teardown, because a link can point anywhere. Only a Homebrew cask's link counts as the app itself. A cask counts only if its Caskroom entry resolves to the selected bundle. A bundle that both Caskrooms point at counts as no cask, like one that two different tokens point at.
- **Package apps**: `find_package_apps` in [`apps.rs`](../src/core/apps.rs) finds apps that an installer package put outside the app folders. It reads each receipt in `/private/var/db/receipts` (the id is the file name, `com.apple.` ids are skipped), takes `InstallPrefixPath`, and runs `pkgutil --files` for the package, because `pkgutil --file-info` prints no package id for such a bundle. A package with an app in an app folder is skipped, since its other bundles belong to that app. Only folders that are not links, at most 4 parts below `/Library/Application Support`, inside no other `.app`, and with no `com.apple.` part, count. Packages put stand-alone apps there. Other system folders hold plug-ins and parts of macOS, and a receipt alone does not prove that a bundle in them is an app of its own. Each app carries the receipt id in `InstalledApp::package`.
- **Apps from an installer package**: an app from `find_package_apps` is not in an app folder, so `can_uninstall` refuses it. `Safety::can_uninstall_package_app` takes it instead, after the same general checks. It uses the same folder rules as `find_package_apps`, and needs a valid package id that is not `com.apple.` and a receipt in `/private/var/db/receipts` whose `InstallPrefixPath` holds the bundle. The plan, `check_job`, and `remove_bundle` use it when `InstalledApp::package` is set. `check_job` also runs `pkgutil --files` again (`apps::package_holds`): the bundle must still be a top-level app of the package, and the package must have no app in an app folder. Otherwise the job fails with `Safety check failed: app is not one an installer package put here`. The plan adds a receipt row for the package, so root runs `pkgutil --forget` after the bundle goes.
- **Order**: before the first password step, an app is only asked to quit, and Homebrew removes casks. That step removes the bundles the user cannot remove, so a refused prompt keeps those apps installed and working. Whatever hurts an app that stays comes after it: unloading, removing login items, signals. The bundle goes to the Trash as the user first, even when the app has receipts or root files. It goes in the root script only when the user cannot remove it (`user_can_remove` or `tree_is_removable` fails), which is also what the review row shows as "(Permanent)". Root files and receipts wait until the bundle is gone, then run in a later root step. A refused password keeps those files, and the failure says the app is already gone. A Trash error never reaches root: the app and its files stay, and the failure carries the App Management or Full Disk Access hint. An app's files go only after the app is gone. Before removing a bundle as the user, taert walks it for anything locked, so a removal does not stop halfway. If the `osascript` call that removes the login item fails, the report gets a note. A selected copy that fails counts as an app that stays from then on, and root files shared by two selected copies wait for both.
- **Identity**: every path is checked again right before removal, by device and inode, and the bundle by its id.
- **Processes**: taert finds them by where their program lives, so a name cannot be spoofed. If taert runs from the app, in one of its terminals, the app is neither asked to quit nor signalled.
- **Root**: each password step runs as one script. Most runs have one step, and a run can have a second one for root files that wait for their bundle to go to the Trash, for example after a bundle the user cannot remove. An uninstall whose plan needs root (`uninstaller::needs_password`) asks for the password once before the first step starts: the TUI calls `AdminGate::ask` in `start_removal`, and `run_uninstall` in `main.rs` calls `AdminSession::prepare`. A refusal does not stop the run, and each root step then fails with `NOT_GIVEN`. Without a terminal, each root step shows the dialog, and after a refused dialog the next step does not ask again. The order of the steps does not change. taert uses `sudo` if it has a cached session, and the macOS password dialog otherwise. The sudo session lives in [`admin.rs`](../src/core/admin.rs): one per run, with `AdminSession::prepare` asking for the password once through `sudo -v` on the terminal. A ticket the terminal already has is used and left alone. While taert holds a ticket, a thread runs `sudo -n -v` every 60 seconds to keep it. On exit, `main` ends the session, and `sudo -k` runs only for a ticket taert started. Without a terminal, `prepare` asks nothing and root steps show the macOS dialog. A standard account gets the dialog for each root step too, because sudo does not let it in, and `will_prompt` is false for it. `Host::is_admin` reads the groups from `id -Gn` and counts a failed run as admin. A password refused at the terminal is remembered for the run, and the dialog is not shown after it. The TUI hands the terminal to sudo in [`terminal.rs`](../src/ui/terminal.rs): `AdminGate::ask` calls `prepare` inside `release_terminal` only when `will_prompt` says sudo would ask. `release_terminal` leaves raw mode and the alternate screen, runs sudo, enters them again, and drops every key waiting, so an Enter typed for sudo does not reach the TUI. `main_loop` clears the screen once before the next draw. `ask` runs on the UI thread only. When the process ends without running `Drop` (Ctrl-C in a plain terminal run), the ticket ends after sudo's own timeout, 5 minutes by default. Paths are quoted. `Safety::is_safe_as_root` refuses a target below a folder the user could replace, because `rm` run as root follows folder links, and the script compares device and inode again right before each `rm`, since the password prompt can stay open for minutes. The Touch ID tip comes from `admin::touch_id_hint`, which reads `etc/pam.d/sudo_local` and `etc/pam.d/sudo` through the `Layout` and runs `bioutil -c`. `AdminSession::take_hint` is true once, after taert's own `sudo -v` succeeded. The CLI prints the tip on stderr after `prepare` in `main.rs`, and the TUI prints it after leaving the alternate screen (`AdminGate::quit_hint`), with ` Or turn it on in taert Settings › Permissions.` added. Settings › Permissions can write `/etc/pam.d/sudo_local` as root, and no other file in `/etc/pam.d`, through `admin::set_touch_id` and one `Host::run_admin` script after `AdminGate::ask`. `admin::touch_id_change` decides first, without a password: it refuses when `/etc/pam.d/sudo` has no `auth include sudo_local` line, or when `sudo_local` is a link, not a file, or holds text other than Apple's template or taert's "on" text (both are constants in `admin.rs`; turning off needs exactly the "on" text). The script sets `PATH` and stops with an error when `sudo_local` is a link or holds text other than the template and the "on" text (`cmp -s`), so a change between the dialog and the password writes nothing. Then it writes the text to `sudo_local.taert-tmp`, sets `root:wheel` and mode `0444`, and renames it over `sudo_local` with `mv -f`. No part of it comes from user input, and every path comes from `Layout::system`. The live test is `tests/touch_id_live.rs`, ignored, for the owner to run by hand.

Everything that touches the running system goes through the `Host` trait in [`host.rs`](../src/core/host.rs), and `Layout` in [`layout.rs`](../src/core/layout.rs) holds the system's folders. Tests use a fake host and a temporary folder, so they never quit an app or ask for a password. `Host` also has `has_tty`, `is_admin`, and `sudo_validate`, which the sudo session uses to ask for the password once per run; the fake host answers all three and records the ask.

## Homebrew

[`homebrew.rs`](../src/core/homebrew.rs) lists installed formulae and casks, finds what is unused, and removes it through brew. The list itself only reads.

- **Finding brew**: the first prefix from `Layout::homebrew_prefixes` (`/opt/homebrew`, then `/usr/local`) that has `bin/brew`. The uninstaller removes a cask with the brew of the prefix whose Caskroom holds it (`brew_in`). If that prefix has no brew, Homebrew does not track the cask, and the bundle is removed as on a Mac without Homebrew. Without a `brew`, the scan is empty with the note `Homebrew is not installed.` and no command runs.
- **Running brew**: only through `Host`, as `/usr/bin/env` with `HOMEBREW_NO_AUTO_UPDATE=1`, `HOMEBREW_NO_ENV_HINTS=1`, and `NONINTERACTIVE=1`, so brew neither updates itself nor asks questions.
- **Two reads**: `brew info --json=v2 --installed`; both reads use a 60 second timeout. A failed call or output taert cannot parse is an error, never an empty list. In the list opened from the main menu, a failed `brew info` read shows as this message instead of rows. Then `brew outdated --json=v2`, which runs only when `brew info` listed packages and gives the new version of each outdated package (`latest_version`), matched by name or full name within formulae and casks apart. If that call fails or its output is unreadable, the scan adds a note and leaves `latest_version` as `None`.
- **Update check**: `taert brew --plain` and `--json` never run `brew update`. The interface runs `homebrew::update` (`brew update`, 5 minute timeout) and then `homebrew::outdated` on a thread, once per run, when the list first shows (`App` keeps the flag). The list opened from the main menu starts it when the scan ends. The list opened by `taert brew` (`App::with_brew_list`) keeps the brew path and starts the check when the run starts, so the constructor runs no command. The list shows `Checking for updates…` meanwhile. The result goes through `Inventory::apply_latest`, which sets `latest_version` and returns the rows whose label changed, and `SelectState::finish_update_check` renames those rows in place, so selection, sort, search, and open rows stay. The label holds no version of the update, so only a pin that `brew outdated` finds for a cask changes a label. The focus stays on the same package, found again by its new label, also when a search is active. Nothing else is read again and no size is measured again. If `brew update` fails, `brew outdated` still runs and a toast shows the last line of stderr. The check goes on when the list is left: `go_back` keeps the receiver on `App`, and the main loop polls it whatever screen is shown. A Homebrew list built while it runs gets `checking_updates`. When the check ends, its result goes to the Homebrew list if one is on screen. Otherwise it is dropped and the next opening uses its own read.
- **Upgrade from the list**: `u` and `⇧U` put an `UpgradePlan` (the brew and the packages, chosen with `upgrade_refusal`) on `SelectState::upgrade`. While `checking_updates` is set they only show a toast, so `brew upgrade` never runs beside `brew update`. While `refreshing` is set they also only show a toast. After `fail_refresh` they work again on the rows the list has. The question, the progress, and the result use the pending plan to pick their wording (`RunKind::Upgrade`), so the scan id alone does not decide. The run calls `homebrew::upgrade` once per package on a thread and writes nothing to the history. When the result closes, `homebrew::refresh` reads `brew info --json=v2 --installed` and `brew outdated --json=v2` on a thread (never `brew update`). It measures only the packages that are new or whose version changed, and every other package keeps its size. `SelectState::finish_refresh` then rebuilds the list with the sort, the search, the open rows, and the focus on the same package. The read waits while any dialog is open on the list: `poll_brew_refresh` takes no result until the overlay closes. An uninstall that ends during the read starts it again when its outcome closes, so the read cannot bring the formula back. A failed read, or a read thread that stops without an answer (`the read stopped`), shows the toast `Could not update the list: ` and keeps the rows.
- **Used by**: worked out from the dependencies in that same JSON. A formula is used by every installed formula that lists its name or full name. taert never calls `brew uses`, which is slow.
- **Tree**: the terminal list is built from the `dependencies` of that same JSON, with no new call. `top_level` splits the formulae into those installed on request, those nothing installed needs (found by following `dependencies` from the requested ones), and the rest. `dependencies_of` gives the installed children of a formula, matched by name or full name, largest first. `tree_sections` lists the rows and sorts each level (the top-level rows of a group and the children of every open row) with the sort the list passes in, so `src/core` does not import `crate::ui`. The install date comes from the same `brew info` reading: the newest keg `time` of a formula, or the `installed_time` of a cask. It is `Package.installed_at`, skipped by serde, so it is not in `--json`. Each row is keyed by its path of names from the top, so a dependency under two formulae opens on its own, and a name that repeats in its own path does not open. `SelectState` keeps the open paths.
- **Sizes**: `DirSizer` measures `<prefix>/Cellar/<name>` for a formula and `<prefix>/Caskroom/<token>` for a cask.

### Cleanup

`taert brew cleanup` finds unused dependencies and old versions with three read commands: `brew info --json=v2 --installed`, `brew autoremove --dry-run`, and `brew cleanup --dry-run`. Each row carries a `BrewTask`, and `Cleaner` hands it to `homebrew::run_task` before any file logic, like a Docker object. A brew row never reaches the path checks.

- **Through brew only**: a removal is `brew uninstall <name>` or `brew cleanup <name>`, never `rm` on the Cellar, so Homebrew's records of what is installed stay right. taert never passes `--force`, `--zap`, or `--ignore-dependencies`.
- **`HOMEBREW_NO_AUTOREMOVE=1`**: Homebrew runs `autoremove` at the end of `brew uninstall` unless this is set. Without it, removing one selected formula would also remove every other unused formula. Every call that removes something sets it. The dry runs and `brew info` keep the usual environment. One helper builds both environments, so the common part is written once.
- **Read again before each uninstall**: `run_task` runs `brew info` again right before the first `brew uninstall` of that formula. If the formula is gone, or `refusal` refuses it by now (pinned, or another formula lists it as a dependency), it returns an error and runs no `uninstall`. So a formula pinned while the list was open, or while the question waited, stays. The run goes on with the next row.
- **Every version**: `brew uninstall` without `--force` removes one version at a time, so taert repeats it until no version folder is left, and stops when a call removes nothing. Brew keeps the formula's folder when it holds another file, so taert checks the version folders, not the folder itself. With no version folder before the first call, taert runs no `uninstall` and returns an error.
- **Order**: a formula comes before every formula it depends on, so a dependency is reached after the formula that used it is gone. Otherwise the biggest row comes first.
- **Freed bytes**: `DirSizer` measures `<prefix>/Cellar/<name>` before and after the call, and the difference is what the history and the report show. The sizes brew prints are not used.
- **Old versions and unused dependencies do not overlap**: an uninstall removes every version, so a formula in the first group is left out of the second, and its size is counted once.

### Remove one formula or cask

`taert brew uninstall <name>` and the `d` key on the Homebrew list remove one formula, or one cask without an app, through the same `homebrew::run_task` path as the cleanup. There is no second removal path. `uninstall_plan`, `refusal`, and the list run no removing call.

- **Plan**: `uninstall_plan` makes one `brew info` call, finds a formula by name or full name first and a cask by token second, and returns a scan with one selected row that carries a `BrewTask::Uninstall` (formula) or `BrewTask::UninstallCask` (cask).
- **Refusals**: `refusal` is the one place that decides. In this order: the cask `taert`, a cask with an app, a cask with other artifacts, a pinned package, a formula that other formulae use. `Package.removal` (`Removal::Formula`, `App`, `Plain`, or `Other(kinds)`) comes from the `artifacts` of `brew info`: an `app` makes it `App`; `binary`, `font`, `manpage`, the completions, and `generate_completions_from_executable` make it `Plain`; any other kind makes it `Other`. `zap` and the `target` key of an artifact are ignored, because `zap` runs only with `--zap`. The CLI prints its text as an error. The TUI shows it on the screen and opens no question. The text for a formula in use comes from one function that `run_task` shares, so the two never differ.
- **The list carries tasks**: `Inventory` remembers the brew that listed the packages, so `list_scan` puts a `BrewTask::Uninstall` on every formula row and a `BrewTask::UninstallCask` on every `Plain` cask row. Other cask rows have none. The scan keeps one item per package (the tree may show it in several rows), with no check marks. `d` selects the focused row alone before it opens the existing confirm dialog. `list_refusals` gives the TUI the refusal of each row by the kind and label of the row.
- **After the removal**: when the outcome dialog closes, the removed package leaves the list and, for a formula, the formulae it used are updated (`Inventory::forget(kind, name)`), without reading Homebrew again. The list keeps the inventory it was built from. Opening the list from the menu, or running `taert brew`, reads Homebrew again.
- **A cask removal**: `uninstall_cask` reads the packages again, refuses with the same `refusal`, runs `brew uninstall --cask <full name>` through `run_removing` (`HOMEBREW_NO_AUTOREMOVE=1`), and fails with `Homebrew removed part of <name>; it is still installed.` when the Caskroom folder is still there. The bytes freed are the size of that folder before and after.
- **A cask with an app**: `d` on it in the TUI finds the installed app whose bundle the cask holds (`apps::find_apps`, then `uninstaller::apps_of_cask`) and opens the uninstall review as Uninstall Apps does. The Homebrew list waits on the back stack (`ReturnPoint::Select`), so Esc returns to it as it was. When the review ends with a removal, the list comes back without the casks whose Caskroom folder is gone, and Homebrew is not read again.

## Orphaned App Files

[`orphans.rs`](../src/core/orphans.rs) finds files and containers left behind in `~/Library` by apps that have been removed.

- **How an id is orphaned**: taert inspects the top level of 11 folders apps use (`Application Scripts`, `Application Support`, `Caches`, `Containers`, `Cookies`, `Group Containers`, `HTTPStorages`, `Logs`, `Preferences`, `Saved Application State`, `WebKit`). Names are trimmed of suffixes (`.plist`, `.binarycookies`, `.savedState`) or stripped of group/team prefixes, while `Containers` folders resolve their id from metadata plists (`MCMMetadataIdentifier`). Every candidate must pass `apps::is_reverse_dns`. Candidates starting with `com.apple.` are skipped. An id is orphaned when no installed app or embedded helper/login item claims it, and for shared group containers when no installed app shares its vendor token.
- **Spotlight check**: for each surviving id, taert runs `mdfind` for `kMDItemCFBundleIdentifier == '{id}'`. If Spotlight finds an app anywhere on connected volumes (including in the Trash), the candidate is dropped. If Spotlight fails, the row remains but starts unselected.
- **Per-item Trash mode**: Orphaned files in `Application Support` and `Containers` often contain user data. When cleaning, `cleaner::remove_selected` splits items into Trash and Permanent batches using `cleaner::item_removal_mode`. Orphan rows move to the Trash by default, while caches and logs in the same scan are deleted permanently.

## Trash vs Permanent Removal

Items slated for removal are classified via `cleaner::item_removal_mode`:
- **Personal files, user apps, and orphaned files**: user app bundles, orphaned files (`taert clean orphans`), and leftovers in home folders (`~/Library`, `~/.config`, etc.) move to the Trash by default via `NSFileManager` (`Host::trash`). In Explore Storage (`taert analyze`), users can choose between "Move to Trash" (default) and "Delete Permanently".
- **Permanent removal**: caches and logs (`taert clean`), build artifacts (`taert purge`), Docker objects (`taert docker`), emptying the Trash, root files (`/Library/...`), and items with `contents_only = true` are permanently deleted.
- **Uninstall plans**: rows of an uninstall plan go by `uninstaller::route`, worked out once per plan and shared by the review, the confirmation, and the run. A cask bundle goes to Homebrew. Receipts, and rows or bundles the user cannot remove, go to root and are removed permanently. Everything else goes to the Trash unless `--permanent` is set.
- **`--permanent` override**: passing `--permanent` forces permanent deletion across all subcommands, bypassing the Trash.
- **Reporting**: outcomes and progress report both `trashed_bytes` ("Moved X to the Trash. Empty it to get the space back.") and `freed_bytes` ("Removed Y permanently."). Slim, compress, and iCloud results are exceptions. A slim result shows `freed_bytes` as "Saved Y of Intel code." under `Slim Complete`, or `Nothing was slimmed`, and `trashed_bytes` is always 0. A compress result shows `freed_bytes` as "Saved Y by compressing N files." under `Compress Complete`, or `Nothing was compressed`. An iCloud result shows `freed_bytes` as "Removed local copies of N files. Freed Y." under `Local Copies Removed`, or `No local copies were removed`. The failure header names the kind of run (remove, slim, compress, or "Could not remove the local copy of N files" for iCloud).

## Startup and Background Items

[`startup.rs`](../src/core/startup.rs) manages launchd services (user agents, system agents, daemons) and classic login items:

- **Launchd Management**: Inspects disabled states (`launchctl print-disabled`) and running services (`launchctl print gui/<uid>` and `launchctl print system`, both on every scan, since neither needs root). A service from the system domain is a daemon, also when it has no plist on disk. Services are associated with installed applications via program path or bundle IDs. A disabled item that still runs keeps both facts: its state is `disabled` and it has a pid. The screen offers "stop" for it, which boots the service out.
- **Ordered Teardown**: When disabling a launchd service, `taert` executes `launchctl disable` *before* `launchctl bootout`. This prevents `launchd` from immediately respawning the job when stopped.
- **Real State**: After `disable`, `enable`, or `stop`, `taert` reads `print-disabled` and `print` again and reports what launchd says. A step that failed, or a result that differs from the request, is an error. A daemon script exits non-zero when `disable` fails.
- **Domain Separation**: User launch agents operate in the `gui/<uid>/` domain without elevation (`Host::run`). System daemons operate in `system/` and require root elevation via `Host::run_admin`.
- **Services an app registered**: A launchd service with no plist in `~/Library/LaunchAgents`, `/Library/LaunchAgents`, or `/Library/LaunchDaemons` is read-only. That covers a service an app submitted (`path = (submitted by ...)`) and one whose plist lives elsewhere, such as in `~/Library/Application Support`. launchd forgets such a service after `bootout`, so taert could not switch it back on. The reason tells the user to switch it in System Settings > General > Login Items & Extensions, or in the app. The Apple rules below apply first. The row keeps a plist path only when the plist sits in the folder of its own domain: `/Library/LaunchDaemons` for a daemon, a `LaunchAgents` folder for an agent. So root never bootstraps a plist from the home folder. A plist that the scan already read under another label stays with that row, so a broken old label never offers to remove the file the new label runs from. A NetworkExtension service is named after the `.systemextension` bundle its program runs from, or after its label without the `NetworkExtension.` prefix and the version.
- **System Events & Login Items**: Discovered via AppleScript (`osascript`) through System Events. When disabled, items are recorded in `~/.config/taert/disabled_login_items.json` and deleted from Login Items; enabling re-creates them via AppleScript. The path is saved before the item is removed. If the save fails, the item stays. taert never writes over a `disabled_login_items.json` it cannot read: switching a login item off then fails with an error that names the file, the item stays, and the scan adds a note. The path goes to AppleScript as an argument (`on run argv`), never inside the script text. If Automation permissions are refused by macOS, `taert` adds a note that shows in the TUI, in `--plain`, and in `--json`, without crashing or corrupting other items.
- **Background Task Management (`--all`)**: `sfltool dumpbtm` runs as root and prints to a pipe that taert reads (`Host::run_admin_output`). Root writes to no file, so a link planted by a user process has nothing to follow. The command has its own 2 minute timeout, which includes the time to type the password. `parse_btm` ignores lines it does not know. Entries that no other source listed show as read-only `background item` rows. Output the parser cannot read gives a note and no rows. The TUI reads the dump once per scan and reuses it after each change.
- **Safety Gate**:
  - Apple system items are hidden by default, excluded from user scans unless `--all` is passed, and strictly refused for modification or deletion. An item is Apple's when its label starts with `com.apple.`. A service that launchd lists without a plist in the standard folders is also Apple's when its plist or program sits in a system folder (`/System`, `/usr/bin`, `/usr/sbin`, `/usr/libexec`, `/usr/lib`, `/bin`, `/sbin`), such as `com.openssh.ssh-agent` or `org.cups.cupsd`, or when its `parent bundle identifier` starts with `com.apple.`. So is such a daemon when launchd shows none of its files, unless its `parent bundle identifier` names an app outside Apple. That daemon belongs to the app: it shows by default and is read-only. An agent that an app registered shows no files either, so it is not taken for Apple's. A `path = (submitted by ...)` value is no file. taert reads only the lines of the service's own block, so the `path` of a socket inside it is never taken for the plist. A line that ends with `{` opens a nested block and a line that ends with `}` closes one, because launchd opens blocks with `= {` and with `=> {`, and a value it cannot print leaves the `}` at the end of that line.
  - Security agents (CrowdStrike, SentinelOne, Jamf, Carbon Black, etc.) are protected and read-only, login items included.
  - `disable` and `enable` on the command line take a label. A login item can also be named by its name or by its path. A name that fits several items is an error that lists them, with the path of each login item.
  - `taert uninstall` removes only the login item with the app's name and the path of the copy it removes.
  - Broken items: user launch agents whose target binary is missing from disk can be permanently deleted after explicit confirmation, verified by `Safety::can_remove`.
  - `taert doctor` quits a process by sending `SIGTERM` after a confirmation that starts with focus on Cancel. `Host::signal` returns a `Result`, and a failed signal keeps the finding and shows the error. It refuses pid 0, pid 1, and a pid too large for `pid_t` (which `kill` would read as a negative group) for every caller and sends nothing (`signal_pid`). Implementations provide `raw_signal`, which only `signal` calls. A finding for pid 0 or 1 says it is part of macOS instead of advising to quit it.
  - `taert doctor` offers `taert startup disable` for a broken item only when the item has no read-only reason. Otherwise the finding shows the reason and has no action.
  - Startup Items and Doctor call `AdminGate::ask` before a daemon switch, and `taert startup` calls `AdminSession::prepare` before a daemon switch and before every `--all` read.

## Universal App Slimming

[`slim.rs`](../src/core/slim.rs) removes Intel (`x86_64` / `i386`) architecture slices from universal macOS applications on Apple Silicon Macs, reducing application footprint while strictly preserving native ARM functionality and code signatures:

1. **Direct Mach-O Fat Header Parsing**:
   - Fat binary headers on disk are big-endian with magic `0xCAFEBABE` (32-bit `fat_arch`, 20 bytes per record) or `0xCAFEBABF` (64-bit `fat_arch_64`, 32 bytes per record).
   - **Java Class Rejection**: Java bytecode `.class` files share the `0xCAFEBABE` magic but store version integers (e.g. `0x00000034` for Java 8) in the subsequent 4 bytes. `slim.rs` enforces `nfat_arch > 0 && nfat_arch < 8`, safely rejecting non-Mach-O files.

2. **Slice Rewriting & Alignment**:
   - Slices for ARM architectures (`CPU_TYPE_ARM64` and `CPU_TYPE_ARM64_32`) are kept; x86 slices (`CPU_TYPE_X86_64` and `CPU_TYPE_I386`) are stripped.
   - Slices are extracted byte-for-byte and written to new offsets obeying standard Mach-O power-of-two page alignments (`1 << align`, typically 16 KiB / $2^{14}$).
   - Binaries lacking any ARM slice are refused immediately without modification.

3. **Code Signature & Resource Seal Integrity**:
   - Files catalogued in `_CodeSignature/CodeResources` with whole-file hashes (`hash` / `hash2` without `cdhash`) are sealed resources. Modifying any file sealed by whole-file hash breaks the bundle's signature. `read_sealed_hashes` inspects `CodeResources` and `find_universal_binaries` skips any file whose whole-file hash is sealed.
   - **Nested seals**: a file under `Contents` is checked against the seal of its nearest enclosing nested bundle. That is a folder below `Contents` with `Contents/_CodeSignature/CodeResources` (keys relative to `<nested>/Contents`), `Versions/<v>/_CodeSignature/CodeResources` or `Versions/<v>/Resources/CodeResources` (keys relative to `<nested>/Versions/<v>`), or `_CodeSignature/CodeResources` (keys relative to `<nested>`). A file with no nested bundle uses the top-level seal. A nested seal that cannot be read leaves its files alone.
   - Mach-O code slices contain their own embedded signatures (`LC_CODE_SIGNATURE`) with individual slice `cdhash` values. Rewriting the outer fat binary header while preserving the ARM slice byte-for-byte keeps the embedded code signature valid.

4. **Transactional 8-Step Pipeline**:
   - **Checks before step 1**: `check_ownership` walks the bundle with `symlink_metadata`. A bundle path that is a symlink is refused ("The app is a link. Slim the app it points to"), because `ditto` would copy the target and the swap would put that copy where the link was. Every entry must have the uid of the user taert runs for (`Host::uid`; uid 0 does not pass) and no setuid or setgid bit. `slim_app` runs it again, then takes a `fingerprint` of the bundle: a hash over every entry's relative path, type, size, mtime in nanoseconds, inode, and device, in sorted order, without following links.
   - **Step 1 (APFS Clone)**: Creates the holding folder `<parent>/<name>.taert-slim-tmp` with mode 0700. If it exists (`AlreadyExists`), the call fails with step 1 and names the folder; it is never removed or moved, because it can hold the only copy of an app from an earlier run. Clones the app to `<holding>/<name>` using `/usr/bin/ditto --clone` on APFS, sharing blocks with copy-on-write. A failed `ditto` removes the holding folder. The admin helper does not run `ditto`; see [Slim as root](#slim-as-root). `candidate_apps` leaves an app inside a holding folder out of `slim_scan`, the `--json` list, and `taert slim <name>`.
   - **Step 2 (Thin Binaries)**: Rewrites fat binaries inside the clone, discarding Intel slices. It opens each binary from the clone one path part at a time with `O_NOFOLLOW`, so a link anywhere in the path stops the step, and it writes through that handle, so the binary keeps the mode it has in the clone. Nothing is read from the original app. The saved size of each file is its allocated size (`DirSizer::allocated_size`) before minus after.
   - **Step 3 (ARM Check)**: Verifies that rewritten binaries retain valid ARM code slices.
   - **Step 4 and 5 (Codesign & Gatekeeper Verification)**: Runs `codesign --verify --deep --strict` and `spctl -a -t exec` on the clone. Only a failed `codesign` check removes the FinderInfo and ResourceFork extended attributes (`removexattr` with `XATTR_NOFOLLOW`) and checks both again once. A failed `spctl` check after a passing `codesign` check fails step 4.
   - **Step 6 (Original State Check)**: Takes the fingerprint again and compares it with the first one, then lists processes with `ps`, then swaps. A different fingerprint ("Original app changed"), a running program (`processes::bundle_is_running`, the check compress uses), or a failed `ps` (`processes::read` returns `None`) fails the step.
   - **Step 7 (Atomic Swap)**: Atomically exchanges the clone and the original app bundle using `renamex_np(RENAME_SWAP)`.
   - **Step 8 (Trash Old App)**: Moves `<holding>/<name>` (the old app, so the Trash item is named like the app) to the Trash using `Host::trash`, then removes the empty holding folder with `fs::remove_dir`. If the Trash call fails, `slim_app` still returns `Ok(SlimDone)` with `old_app` set to the old app's path and the error text. If the Trash call succeeds but `fs::remove_dir` fails, `holding_left` holds the folder and the error, because the next run stops at that folder. `SlimDone::summary` builds the line the CLI, the plain picker, and the interface print for a finished slim.
   - **Rollback**: An error up to step 7 leaves the original app as it was and removes the holding folder when it is still the folder this run made. A folder that was put in its place stays. After the swap nothing is removed.
   - **Programs**: `slim.rs` starts `ditto`, `codesign`, `spctl`, and `sysctl` by full path (`/usr/bin/ditto`, `/usr/bin/codesign`, `/usr/sbin/spctl`, `/usr/sbin/sysctl`), so the helper that runs as root never starts a program from the `PATH` of the user.
   - **Who slims**: `check_eligibility` takes `SlimRules` (Rosetta apps, running programs, `skip_developer_id`, `system_owner`) and returns `Eligible { binaries, needs_admin }`. An app whose every entry belongs to `system_owner` (0 in production) has `needs_admin`, and only when it lies directly in `/Applications`; elsewhere it is refused with `taert slims apps that belong to root only directly in /Applications`. `slim_scan` copies the flag to `ScanItem.needs_admin`, and `--json` prints `needs_admin` only when true. The interface asks `AdminGate::ask` before the worker starts, and the CLI asks `AdminSession::prepare` after the confirmation; both then call `slim::slim_logged`, which runs `admin::run_slim_helper` for such an app and records the history once.
   - **Everywhere**: `check_eligibility` always runs `codesign --verify --deep --strict` and `spctl` after the "Already Apple Silicon only" check, so `slim_scan`, the `--json` list, and `taert slim <name>` agree.

   - **Apps that belong to root**: steps 1 to 7 are the function `slim_to_swap`, which takes the uid that must own every entry, the holding folder to make, and, for the helper, `RootSteps`: how to make the copy, how to check it, which binaries in it to slim, and a guard that runs before the swap. `slim_app` runs it with `Host::uid` and `<parent>/<name>.taert-slim-tmp`. The helper job `slim` runs it as root with owner 0 and a holding folder in `/Library/Application Support/taert/slim`, so the holding folder (mode 0700) and the copy belong to root, and the swap puts the slimmed copy in place. The user cannot do this: the copy would belong to the user, and the swap needs rights the user does not have. See [Slim as root](#slim-as-root).
   - **Holding folder check**: after `mkdir`, `slim_to_swap` opens the holding folder without following a link and checks that it belongs to the owner and has mode 0700. Otherwise step 1 fails and the folder is left as it is, because another process can put its own folder at that path right after the `mkdir`. Then it remembers the device and inode of that folder. If the folder is not that folder before the swap, the swap does not happen, and the folder is left as it is.

5. **Block Reclamation**:
   Because the cloned app initially shares blocks with the original via copy-on-write (`EF_SHARES_ALL_BLOCKS`), rewriting binary files copies only the modified fat header blocks. Moving the original to the Trash preserves recoverability, and the freed space is returned to APFS when the user empties the Trash.

## Transparent APFS Compression

[`compress.rs`](../src/core/compress.rs) implements transparent APFS file compression utilizing macOS kernel-level decmpfs support:

1. **decmpfs Format & ABI**:
   - Files are compressed using Apple's `libcompression` framework with LZFSE (type 12). The code writes no other type.
   - Data is split into 64 KiB blocks. Each block is compressed on its own. A file whose blocks do not shrink enough to save 4 KB is skipped.
   - The file is read and compressed one block at a time, so a large file never sits in memory whole. The offset table is written last, once all block sizes are known.
   - The compressed blocks go to the resource fork stream via `path.join("..namedfork").join("rsrc")`. This bypasses the `setxattr` system call's 4 MB `E2BIG` limit.
   - The `com.apple.decmpfs` extended attribute (16-byte header: magic `0x636d7066`, compression type 12, uncompressed size `u64`) is attached, and BSD flag `UF_COMPRESSED` (`0x0020`) is set via `fchflags`.
   - Apps that rewrite a compressed file unpack it, and the next update puts back the plain bytes. Run `taert compress` again after app and package updates.

2. **Atomic 4-Step Safety Pipeline**:
   `compress_file` and `undo_file` build a copy beside the file and swap it in only when it checks out:
   - **Step 1 (Temp file)**: Writes the data to a temporary file `.<name>.taert-tmp-<pid>-<nanos>-<seq>.tmp` in the same folder. The file is created with mode `0600`, so no other user can read the copy while it is verified, and any ACL it inherits from the folder is cleared. Then it gets the extended attribute `io.github.ingvarch.taert.copy`, which marks it as taert's copy. A guard removes it on every error, including an undo that runs out of space. The guard clears flags and ACL before it unlinks, and the error names the file if the unlink still fails.
   - **Step 2 (Metadata)**: Copies ownership (`fchown`) and flags (`fchflags`), then the extended attributes. Any error fails the file and keeps the original.
   - **Step 3 (Byte-by-byte readback verification)**: Reads the temporary file back through the kernel, which decompresses it, and compares it block by block with the original.
   - **Step 4 (Times, ACL, mode, swap)**: Sets access and modification times and the birth time after the flag, because setting `UF_COMPRESSED` resets the modification time. Then it removes the copy mark and copies the ACL (after the extended attributes, so an ACL that denies `writeextattr` cannot block them) and the mode.
   Right before the swap, the original's inode, size, and modification time must equal what they were when the file was opened. Otherwise the file is left as it is. Right after the swap `renamex_np(..., RENAME_SWAP)`, the old file, now at the temporary path, is checked again. If it is unchanged, it is deleted. If it changed, the swap is undone, so a program that wrote to the old inode loses nothing. The swap is undone only if the path still holds the new copy. If the file was renamed away or replaced in the meantime, the changed old file stays beside it as `<name>.taert-changed-<nanos>` and the error names it.
   The check for open files is one `lsof` listing taken at the start of a run. A program that opens a file after that listing and writes only after the swap is not caught: its writes go to the old file and are lost. The refusals in the next section keep most such files out. Close programs that write to the folder before a long run.

3. **Safe Undo**:
   `taert compress --undo` copies the decompressed kernel stream to a temporary file block by block, runs the same metadata, verification, and swap steps with `UF_COMPRESSED` cleared.

4. **Eligibility & Skip Rules**:
   A file is skipped without modification if:
   - Already compressed (`UF_COMPRESSED` or existing decmpfs/ResourceFork).
   - Has multiple hardlinks (`st_nlink > 1`).
   - Is an APFS clone sharing blocks with another file (`EF_SHARES_ALL_BLOCKS`).
   - Is a cloud or dataless placeholder (`SF_DATALESS`).
   - Is not owned by the current user.
   - Has the `uchg`, `schg`, `uappnd`, or `sappnd` flag, or sits in a folder that has one. In an append-only folder taert could create the temporary file but neither swap nor remove it.
   - Has an ACL that denies `delete`, or sits in a folder whose ACL denies `delete_child`. The swap and the removal of the temporary file would fail.
   - Sits in a folder whose flags cannot be read.
   - Is open for writing. One `lsof` listing at the start of the run names these files. If `lsof` fails, the run changes nothing.
   - Net compression savings are less than 4 KB (or file is under 4 KB).

   Temporary files that earlier runs left behind are deleted when their folder is visited, unless the run that made them is still alive. Flags and ACL on such a file are cleared first. This keeps a stale file out of app bundles, where it would break `codesign --strict`.
   Only a file with the copy mark is deleted. The mark comes off before the swap, so the original never has it, even when a crash or a failed swap back leaves the original at the temporary name. A leftover without the mark is kept and listed as a failure on every run, until you compare it with the file beside it and remove the one you do not need. A crash in one of three short moments leaves an unmarked file, which is listed the same way: right after the temporary file is created and before it is marked, between removing the mark and the swap, and after a swap back before the copy is removed.

5. **Safety Gate (`Safety::can_compress`)**:
   Every caller goes through `Compressor::process_path`, which runs the gate first. The command line and the TUI share it. TUI rows marked `needs_admin` skip it and go to `run_compress_helper`, which runs the gate again as root. The path is made absolute before any check, and after the gate passes the walk starts from the real path, so `..` and a wrong letter case cannot get around the later checks. Compression is strictly limited to safe locations:
   - User home directory (`~`, including `~/.rustup`, `~/.cargo/bin`, toolchains).
   - Application bundles in `/Applications` or `~/Applications`.
   - Homebrew prefix (`/opt/homebrew`, `/usr/local`).
   - Refuses system trees (`/System`, `/usr/bin`, `/sbin`), root trees, and user credential directories (`~/.ssh`, `~/.aws`, `~/.gnupg`, etc.).
   - Refuses the places where apps keep data that changes while they run: `~/Library/Application Support`, `~/Library/Containers`, `~/Library/Group Containers`, `/opt/homebrew/var`, and `/usr/local/var`. A walk skips these folders.
   - Refuses any app bundle that is running. The check applies to a bundle named on the command line and to each bundle met during a walk, so `~/Applications` is covered. It compares the real path of the bundle with the process table. If `ps` fails, the bundle is refused.

6. **Estimates**:
   The TUI estimate for an app, the Homebrew Cellar, or the Rust toolchains compresses a sample of 48 files in memory, picked by size across the tree, and applies the saved fraction to the folder size. Candidates that would save nothing are not listed. `taert compress --dry-run` estimates every file the same way.

7. **Tests in CI**:
   The round-trip tests run in the `check` job of `.github/workflows/ci.yml` on the `macos-latest` runner. A comment on issue #38 records the runner image of the first run that included the tests of the compress fixes. The `macos-26` runner of the `snapshot` job builds a release snapshot and runs no tests. The label `macos-latest` moves to newer macOS versions over time, so read the "Runner Image" lines of the job log for any other run.

## iCloud Local Copies

[`icloud.rs`](../src/core/icloud.rs) lists the folders of `~/Library/Mobile Documents` and asks iCloud to remove the local copy of files it has uploaded. It never deletes a file and never reaches `Cleaner`. `Host::icloud_state` reads the iCloud state of a file and `Host::evict` calls `NSFileManager.evictUbiquitousItemAtURL:error:`, both through `objc2-foundation`.

- **Gate**: `Safety::can_evict` checks, in order: a clean absolute path, a path under `Mobile Documents`, at least two levels below it and not hidden, no link on the way, a regular file without `SF_DATALESS`, the same device and inode as the walk, not ignored, and an iCloud state that allows it (kept by iCloud, downloaded, uploaded, not uploading, no conflicts). An unreadable state refuses.
- **Folders are never removed**: the walk passes only regular files to the gate, the gate refuses anything else and the folders `Mobile Documents`, each container root, and `com~apple~CloudDocs`, and `MacHost::evict` refuses non-files itself.
- **Walk at run time**: a run reads every selected row again instead of keeping a file list from the scan. Only the row folder is compared with the scan. The scan and the run share one walk and one rule.
- **Dataless folders**: a folder with `SF_DATALESS` is not listed, because listing it makes iCloud fetch the names from the network.
- **Freed size**: taken from `st_blocks * 512` just before the call, because iCloud may finish after the call returns.
- **Selection**: a row starts selected when the newest of every file's modification and access time and every folder's modification time is 30 days old or more, and nothing was unreadable.
- **History**: one `changed` line per row with the bytes freed, and one `failed` line per file.

## Admin Helper

[`admin_helper.rs`](../src/core/admin_helper.rs) is the root side of the hidden commands `taert admin-helper compress [--undo] --home <path> <bundle>` and `taert admin-helper slim --home <path> --owner <uid> --group <gid> <bundle>`. [`admin::run_compress_helper`](../src/core/admin.rs) and [`admin::run_slim_helper`](../src/core/admin.rs) start them.

Compress copies owners, flags, attributes, and ACLs, and swaps a copy in with `renamex_np`. In a bundle that belongs to root, the user can do none of this, and `Host::run_admin` runs only shell scripts. So the work runs in a second taert process as root, started with `sudo` or the administrator dialog through `Host::run_admin_output`. The parent runs the script `PATH=/usr/bin:/bin:/usr/sbin:/sbin '<exe>' admin-helper compress ...`, with every part quoted. macOS sudo keeps the PATH of the user, so the script sets its own.

`main` parses `admin-helper` with a parser of its own, `AdminHelperCli` in `src/cli.rs`, before it parses the other commands. So the help and the shell completions do not list the helper, and the global flags, such as `--dry-run`, do not exist for it.

The helper does not trust the parent. Before it writes, `helper_check` checks the bundle again:

- The process runs as root.
- The path is an app bundle in an app folder, and `Safety::is_safe_as_root` passes: every folder between the app folder and the bundle belongs to root, and only root can write in it.
- The bundle is not a link, every entry in it belongs to root, and none is setuid or setgid.
- No folder in the bundle, the bundle included, can be written by others or by a group besides wheel, and none has an access control list. A folder like that would let a user process swap an entry for a link while root works in it.
- `Safety::can_compress_with_host` passes, the check for a running app and for App Management included. App Management applies to root too.

Before each folder and file it changes, the helper checks that the bundle path still has the device and inode it had at the check and is not a link. It stops with an error otherwise. Its `lsof` runs as root, so it sees files that root daemons hold open.

The helper reads two files of the user (`--home`): the ignore list, and the LaunchServices preferences that hold the apps set to open using Rosetta (`slim` only). `--home` must be a full path to a folder that is not a link. One function (`read_user_file`) opens each file without following a link in its last part, without blocking on a pipe, and returns it only when it is a regular file of the owner of `--home`. Folders on the way to it are followed, so a link there can point elsewhere, but the file must still belong to the user, and nothing from it is shown. A missing file means no list and no Rosetta apps; any other problem stops the helper with `Could not read the ignore list` or `Could not read the Rosetta settings`, which quote nothing from the file. Root writes only inside the root-owned bundle and, for slim, in `/Library/Application Support/taert` and the old copy it moves to `/Applications`. It always exits with 0 and prints one JSON object, bad arguments and `--help` included, because a non-zero exit drops the output: `compress` prints the `CompressReport`, `slim` prints `{"saved": N, "old_app": "..."}`, and an error is `{"error": "..."}`, with `"step": N` when `slim` stops at a step. A non-zero exit means that sudo or the dialog failed, for example a refused password, and the parent reports that.

### Slim as root

`slim` first refuses an app that is not directly in `/Applications` with `taert slims apps that belong to root only directly in /Applications`. The swap finds the folders above the app by path, and `/Applications` is the only one of them that a process of the user cannot replace. For an app in a vendor folder, such a process could put a link to any folder in place of the vendor folder, and root would swap the app of that name in that folder. Then `slim` runs `helper_check` (it includes `check_ownership`, so a setuid or setgid file is refused). Then it refuses a bundle with a file that has more than one name (a hard link), because the hand-over below would give the user that file under its other names too, and they can be outside the bundle. Then it runs the rules of `check_eligibility` that do not look at the owner (`check_app_rules`, `check_signed_universal`): not Apple, not from the App Store, not set to open using Rosetta, not running, signed with a Developer ID, an Intel slice to remove, and a passing signature and Gatekeeper check.

The holding folder is not next to the app. `/Applications` is `root:admin 775`, so a process of an admin user could rename a holding folder there and put a link in its place while root copies the app into it and rewrites binaries in it by path. A crafted Mach-O could then make root write chosen bytes to any file. So the helper makes the holding folder `/Library/Application Support/taert/slim/<pid>.<n>` with mode 0700 (`new_holding`). It opens `Library`, `Application Support`, `taert`, and `slim` one by one through descriptors with `O_NOFOLLOW`, and makes `taert` (0755) and `slim` (0700) when they are missing. It refuses unless each folder from `Application Support` down is not a link, belongs to root, cannot be written by group or others, and has no access control list. The clone takes on the inheritable ACLs of the folder it is made in, so an ACL there could give others rights in the copy. It also refuses when `slim` is on another device than the folder of the app, because the swap and the move below work only on one volume.

Steps 1 to 7 run with the copy in that holding folder. Step 1 does not copy what the path of the app names. The helper opens the bundle with `O_NOFOLLOW|O_DIRECTORY`, checks that it still has the device and inode that `helper_check` saw, and clones that descriptor into the open holding folder with `fclonefileat`. So a folder put at the path of the app after the check is never copied. As root, the clone keeps owners, modes, flags, and extended attributes. It does not copy ACLs, and it gives each name of a hard link its own file.

Right after the clone, and again right before the swap, the helper checks the copy (`check_root_copy`): every entry belongs to root, no file is setuid or setgid, and no file has a second name (a hard link). The copy is in a folder only root can write, so checks by path stay true there. After the first check, the rules that read the app run again on the copy: not Apple and not set to open using Rosetta (by the bundle id in the copy), not from the App Store, signed with a Developer ID, and an Intel slice to remove. A process can put another folder at the path of the app while the first run reads it, so step 2 slims the universal binaries found in the copy, not the list from the first run. The first run stays, so a refusal still comes before anything is written when nothing changed. The device and inode guard of the bundle (`BundleId::verify`) runs last before the swap. Errors before the swap print `{"error": "...", "step": N}` and remove the holding folder, which is safe because only root can reach it.

A normal slim moves the old app to the Trash. Root's Trash is one the user never sees, and the user can move an item to their own Trash only when it is theirs. So after the swap the helper gives the old copy and every entry in it to the uid and gid that the parent passes as `--owner` and `--group` (`hand_over`).

The swap works by path, so a process can still put its own folder at the path of the app in the instant before it, and that folder then lands in the holding folder. So the helper first opens the old copy with `O_NOFOLLOW|O_DIRECTORY` and checks that it has the device and inode of the checked bundle. The swap keeps them, so the real old app passes. A folder that does not pass is neither handed over nor moved: it stays in the holding folder, and the answer holds `handover_error`. The walk (`walk_tree`) goes down from that descriptor with `openat(O_NOFOLLOW|O_DIRECTORY)` and changes each entry with `fchownat(..., AT_SYMLINK_NOFOLLOW)`, so a link in the old copy cannot make root change a file outside it. It stops at a file with a second name, because that name can be outside the old copy. The helper does not read `SUDO_UID`, because the dialog path does not set it. Then it moves the old copy with `renamex_np(RENAME_EXCL)` to `/Applications/<name>.taert-old.app`. When that name is taken, it tries `<name>.taert-old 2.app`, `<name>.taert-old 3.app`, and so on, and never replaces an entry. Then it removes the empty holding folder and prints `{"saved": N, "old_app": "/Applications/<name>.taert-old.app"}`. If the hand-over fails, the app is still slimmed, and the helper still moves the checked old copy to `/Applications`, where parts of it still belong to root. The answer then also holds `handover_error`. If the move fails too, or the old copy did not pass the check, `old_app` is the old copy in the holding folder.

The parent (`run_slim_helper`) runs the helper once, so there is at most one dialog. It checks that `old_app` is directly in `/Applications` and has a name the helper gives for that app. Otherwise it reports that it cannot read the answer and moves nothing to the Trash. Then it moves `old_app` to the Trash as the user (`Host::trash`). If the Trash fails, `SlimDone` keeps `old_app` and the error, as in a normal slim.

With `handover_error`, the parent moves nothing to the Trash. When `old_app` is such an old copy in `/Applications`, the summary says that taert could not give it to the user and that it can be moved to the Trash in Finder, which asks for an administrator password. When `old_app` is the app in a holding folder of root (`/Library/Application Support/taert/slim/<folder>/<name>.app`), the summary says that an administrator must remove that holding folder. Any other place is an answer the parent cannot read.

Trade-offs:

- Root runs the binary that taert runs from (`current_exe`). The user can usually write that file, for example a Homebrew install. Whoever can change it can run code as root the next time taert uses sudo.
- `/Applications` is `root:admin 775`, so a process of an admin user can rename entries in it, the bundle included. Root clones the checked bundle from a descriptor and checks the old copy after the swap, so a folder swapped in is never copied, handed over, or moved. The swap itself works by path, so such a process can still put its own folder in place of the app right before it; that folder then stays in the holding folder for an administrator to remove. The app must be directly in `/Applications`, so no link above the app can send the swap to another folder. The holding folder of root is in a folder only root can write, so such a process cannot swap it. The binaries are opened through the copy with `O_NOFOLLOW` on every path part, so a link is not followed.

## APFS Space Accounting

Nominal file lengths (`metadata.len()`) do not reflect actual disk occupancy on APFS due to sparse files, compression, and block clustering:

- **Block Allocation**: `DirSizer` queries macOS `st_blocks` via `std::os::unix::fs::MetadataExt`. Actual allocated storage is computed as `st_blocks * 512`.
- **Hardlink Deduplication**: Files with multiple links (`st_nlink > 1`) are tracked by device and inode number (`FileIdentity { dev, ino }`). Storage blocks are counted once per inode to prevent inflated space estimates.
- **Clone Deduplication**: APFS clones (created by Finder duplicate, `cp -c`, or package managers like pnpm and Bun) share disk blocks despite having distinct inodes. `DirSizer` queries clone identity and extended flags (`EF_SHARES_ALL_BLOCKS`) via `getattrlist` ([`apfs.rs`](../src/core/apfs.rs)). Files sharing all blocks with another file in the same measurement are counted once per clone ID and device. Files that share only part of their blocks count in full, because clone IDs do not specify partial sharing amounts.

Limits:

- A file that has several copies counts once in the total of the measured folder. Each folder below it counts the file once too, if it holds at least one copy. A later copy adds its size only to the folders above it that hold no earlier copy, up to the first folder that already counts the file. So a folder that holds only the second copy shows its full size, and the sizes of sibling folders can add up to more than the parent. One walk gives every folder its own exact size, and the cache drops nothing because of copies.
- A clone whose twin sits outside the measured folder still counts in full, though removing it frees nothing.
- The freed total of a cleanup adds up row sizes, so two rows that share blocks count twice.

## Smart Storage Cache

Explore Storage uses a two-tier in-memory cache ([`StorageCache`](file:///Users/igor/Repos/ingvarch/taert/src/core/cache.rs)):

1. **Subtree Directory Aggregation**:
   When a directory is scanned, `DirSizer` collects all visited subdirectories and direct file sizes. Upon walk completion, directories are sorted from deepest to shallowest and aggregated bottom-up:
   $$\text{size}(D) = \text{direct\_bytes}(D) + \sum_{C \in \text{children}(D)} \text{size}(C)$$
   This pre-computes exact recursive sizes for every subdirectory in the tree in a single pass ($O(D \log D)$ in $< 2\text{ ms}$). A later copy of a file adds its size to `direct_bytes` of its folder and subtracts it from the first folder above that already counts the file, so the sum stays right at every level.
2. **Instant Drill-Down**:
   When navigating into a subfolder, its children's sizes are already present in the cache, packages (`.app`, `.framework`, `.bundle`) included. Directory listings load in $< 1\text{ ms}$ without additional disk traversal. The measuring dialog shows only after 150 ms, so a folder that loads faster opens with no dialog.
3. **Snapshot Caching**:
   Constructed `FolderSnapshot` structures are cached in memory. Re-visiting a previously viewed folder with a fresh snapshot restores the view instantly in the same frame without spawning a background thread.
   `StorageCache::lookup_snapshot` says whether a snapshot is `Fresh` or `Stale` (the folder's mtime changed or the 15-minute TTL passed). A stale snapshot shows at once with `Updating…` on the list frame. `scan_folder` measures the folder again in a background `Job`, and the new rows replace the old ones when it ends. The focus and the Space marks stay on their paths, and the swap waits while a dialog is open. The update stops when the open folder changes (`go_up`, opening another folder, `R`), when a removal starts, and when the user leaves Explore Storage. `tick` starts it again for a level that is still stale. If the update thread ends without a snapshot, the level keeps its old rows and sets `update_failed`, and `Updating…` goes away. The level stays stale, so a removal does not cache its rows as fresh. No update starts for it until you open the folder again.
4. **Cache Invalidation**:
   - Deleting items in Explore Storage invokes `invalidate_prefix` on affected paths and updates parent snapshots. In a stale folder the rows are not cached again, and the level stays stale until an update brings new sizes, or until you open the folder again.
   - Performing cleanup operations from the main menu clears the cache to prevent stale data.
   - Directory modified times (`mtime`) and a 15-minute TTL mark a snapshot stale. A stale snapshot shows at once with `Updating…` and is measured again in the background.
   - Pressing `R` in Explore Storage forces an immediate cache bypass and fresh rescan.
